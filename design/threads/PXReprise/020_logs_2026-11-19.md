## How to run the join on a catalog

The macros have to be created in a writable database. So use an in-memory DuckDB and attach the catalog read-only:

```sql
ATTACH '<catalogs>/catalog-4e486c3dcf0aa01c.duckdb' AS cat (READ_ONLY);
.read <store>/_engine/logs.register_orthology/0fe30fe8d4edc728/snapshot/views.sql
WITH g AS (SELECT DISTINCT gene_id FROM cat.gene_resolutions
           WHERE entry_accession = 'P14136' AND gene_id IS NOT NULL),
     o AS (SELECT o.* FROM orthologs('<store>/_engine/logs.register_orthology/0fe30fe8d4edc728/snapshot',
                                     'homo_sapiens', 'mus_musculus') o JOIN g ON o.gene = g.gene_id)
SELECT o.relationship_type, o.is_high_confidence, o.partner_gene, r.accession, r.outcome
FROM o JOIN cat.gene_resolutions r ON r.gene_id = o.partner_gene;
```

## PXR-O13

### 1. The orthology layer as one repository-wide table

- **One release holds** 13 files in a 9.0 MB tar:
  - genes: 200,649 rows (three species, every biotype);
  - gene-tree members: 64,114 rows;
  - gene pairs: 1,001,934 rows, the orthologs and paralogs as Compara calls them, with one file per species pair.
- **The key is gene-centric.** Rows are keyed by Ensembl stable gene ids. The snapshot is identified by its tag and the
  tar's sha256 (`b1d682a5...`), and it names its gene set per species by sha256. It holds no accession: the step from
  accession to gene is `gene_resolutions`, per searched database.
- **How a catalog should carry it: as it does now.** One copy per store, beside the bundles and never inside them. One
  copy per catalog: dataRepo refuses two. Its id is part of the catalog id.
  - We would keep it as a registered artefact, not flatten it into a core table. It is a versioned file format of ours
    (`format_version` 1), and its views are part of the contract.
- **When the release moves** (Compara 117), the cost is one new snapshot with a new tag, and one gene-resolution run per
  searched database (42 in this catalog). The runs are needed because the gene sets move with the release, and dataRepo
  refuses to build a catalog whose resolutions used other gene sets than the snapshot's. No bundle is touched. An old
  analysis keeps its old tag.

### 2. "Every ortholog of protein X"

1. **Accession to gene**, from the `gene_resolutions` of the database X was searched in. A variant (`P12345_S70N`) or an
   isoform reaches its entry through `entry_accession`. State the outcome:
   - `resolved`: one gene;
   - `multi_gene`: follow each gene and say so;
   - `not_in_source` or `off_primary_only` with no gene: stop and say "X resolves to no gene".
2. **Gene to orthologs:** `orthologs(snapshot, a, b)` for each other species. Keep every row, including one-to-many and
   many-to-many, with `relationship_type` and `is_high_confidence`.
   - With no row, give `pair_status`'s reason: `no_edge_in_shared_tree`, `tree_lacks_target_species` or
     `not_in_any_tree`, or `not_in_gene_set`.
   - Go from X's species to each target directly. Human -> mouse -> rat is not human -> rat; `species_set3` gives
     three-way sets.
3. **Partner gene to accessions:** the `gene_resolutions` rows for that gene in species b's searched databases. This
   brings every isoform and variant those databases hold. An ortholog with no accession is its own answer: "ortholog in
   Compara, no protein in any searched database".
4. **Accessions to peptidoforms and PTM sites**, as you measured.

Paralogs are in the snapshot, but `orthologs()` leaves them out. "Homologs" should be a separate, explicit request,
never mixed into orthologs.

**What a result should say, so a reader can audit it:**
- the catalog id, which pins the snapshot and every gene-resolution artefact;
- X's outcome and the definition (`logs:DEF-GENE-RESOLUTION v1` or `v2`);
- each partner's `relationship_type`, `is_high_confidence` and outcome;
- each refusal as a row. An empty answer reads as "not detected", which is a different claim.

**What the symbol stand-in misses, measured on this catalog.** We took the 16,306 human accessions (16,196 genes) in
`protein_index` that have a gene name, are seen at 1% in at least one dataset, and resolve to exactly one gene. For each, we
compared the partner accessions in `protein_index` found by the same gene name (case-insensitive) with those found by
orthology:

| human accessions whose partners, by symbol and by orthology, are | mouse | rat |
|---|---:|---:|
| the same | 13,141 (80.6%) | 11,036 (67.7%) |
| short of orthology's: the symbol misses some or all of them | 874 | 1,057 |
| beyond orthology's: the symbol adds partners | 1,376 | 2,971 |
| otherwise different | 91 | 168 |
| none either way | 824 | 1,074 |

- **Orthology finds what a symbol misses** in one-to-many families. Human IFNA13 has 10 mouse partner accessions by
  orthology and 1 by name. Immunoglobulin and T-cell receptor segments are the same.
- **What a symbol finds that orthology cannot reach is mostly our gap, not Compara's.** We gave a reason to every
  symbol partner outside the orthology set (counted as pairs):

| why the symbol partner is not an ortholog's accession | mouse | rat |
|---|---:|---:|
| its accession resolves to no gene (`not_in_source`; rat also `off_primary_only`, 344) | 1,126 | 2,834 |
| X's gene has no Compara ortholog in that species | 284 | 260 |
| its gene is in Compara, but not as an ortholog of X's gene | 70 | 115 |

  - The first row is mostly reviewed entries whose UniProt record links no Ensembl gene, and which Ensembl's xref does not
    know either. Examples are Q9QXJ1 (mouse Apbb1) and Q9Z223 (mouse Mocs2).
  - A query should report those as "partner by name, no gene resolution", never quietly fall back to the name.
- **An idea that did not work:** we tried pruning the peptidoform scan by `protein_index.dataset_ids_1pct`. It saved
  nothing. An index by accession is yours to weigh.

The measurement is our `logs_orthology.catalog_orthologs`, run read-only. The tables are
`results/catalog_orthologs_4e486c3dcf0aa01c.md`, and every count above is pinned in `tests/test_reported_claims.py`.
Timings are not pinned.

### 3. Pros and cons of one repository-wide copy, from our side

- **For it:**
  - One release per catalog, enforced. A join across datasets cannot mix Compara releases or gene sets; per-bundle
    copies could, after a release move.
  - 9 MB once, rather than once per bundle.
  - A release move touches no bundle.
  - The catalog id pins everything an analysis joined through.
- **What it costs:**
  - **A bundle downloaded alone has no orthology and no gene resolution.** It can still say what it would join: its
    `bundle.json` names its searched databases by sha256, which is the key of `gene_resolutions`. The catalog's choice of
    snapshot can change after a bundle is frozen, so the bundle should not name one. A download from a catalog could carry
    a small reference manifest instead: the snapshot tag and sha256, and the gene-resolution artefact ids for that
    bundle's databases.
  - **Refusals must travel with the table.** Without `pair_status`, a missing ortholog looks like a protein nobody detected.
  - **A catalog serves one release at a time.** Comparing two Compara releases needs two catalogs.

### 4. Licensing: yes, with attribution

- **Ensembl's release-116 disclaimer** (https://jun2026.archive.ensembl.org/info/about/legal/disclaimer.html; the
  www.ensembl.org page now redirects there) says: "Ensembl imposes
  no restrictions on access to, or use of, the data provided and the software used to analyse and present it", and
  "Ensembl data generated by members of the project are available without restriction".
  - It adds that "some of the data … may be subject to third-party constraints". The only such field we carry is
    `gene_name`, the display names Ensembl imports for genes. We know of no constraint on them, but we have not checked
    each source.
- **Our additions are CC-BY-4.0.** That covers the selection, the structure, the refusal classes and the checks.
  `views.sql` is mzLib's (LGPL-3.0).
- **To redistribute:** cite the tag and the tar's sha256, and Ensembl, as our `LICENSING.md` says.
- **A gap of ours:** the released tar carries no licence file. The terms are in the repository's `LICENSING.md`. If you
  redistribute the tar, put that attribution beside it.

### Comment for #25

> **From logs (cross-species orthology and protein-to-gene resolution).** Both of our outputs already work the way the
> reference-table proposal describes. Gene resolutions are computed once per searched protein database, never per
> dataset. Each row carries the checksums of its inputs (the search database, the Ensembl gene set, Ensembl's UniProt
> cross-reference file) and a definition id (`logs:DEF-GENE-RESOLUTION v1` or `v2`). The orthology snapshot (Ensembl
> Compara, one tagged release per catalog) is registered once per store and read in place; no rows are copied into
> bundles.
>
> We support option B and the reference-table rule, with two additions:
>
> 1. **A reference table's key needs the method version as well as the input checksums.** One database resolved under
>    two versions of a definition gives two artefacts, and they must never share an id.
> 2. **Reference tables can depend on each other.** Our gene resolutions name the gene set they used, and the orthology
>    snapshot names one gene set per species. A catalog should refuse to join the two when those differ, as dataRepo's
>    catalog builder already does.
>
> On layers, we prefer one logs layer that follows the reference-table rule to a single shared `reference` layer. Our
> tables change on their own schedule: a new column this month, and a residue-level correspondence table next. In a
> shared layer versioned as one, each of our changes would cost the other members a version, and each of theirs would
> cost us one. We would treat "reference" as a keying rule rather than as a unit of versioning.

### Comment for #24

> **From logs.** We prefer the column-contract hash in each table file, with both hashes in `bundle.json`, as
> recommended. One addition: a contract hash says that the columns are what a reader expects. It does not say that the
> values mean the same thing. For engine tables, that is the definition id's job (for example
> `logs:DEF-GENE-RESOLUTION v2`). Keep the definition id on the rows or in the run record, beside the contract hash,
> rather than folding it into either hash.
