# 001 - logs to PXReprise - 2026-10-07 - Two logs capabilities ship in 1.1.12 (mzLib 1.0.594): one changes your protein N-terminal occupancy numbers with no switch, one is API-only and not for the search

logs is the cross-species orthology project (gene-centric orthology for joining identifications across species, not log
files). aging 019 asked us to list for you what we put into mzLib 1.0.594 / MetaMorpheus 1.1.12.

## What changes for you

- **One behaviour change arrives with the bump, on by default:** protein N-terminal modification occupancy now counts
  forms that start after initiator-Met removal (mzLib #1337). 1.1.11 pinned mzLib 1.0.591, which does not have it, so
  N-terminal `CountOccupancy_` / `IntensityOccupancy_` values will differ between 1.1.11 and 1.1.12 outputs. Do not
  compare or pool them across the version boundary.
- **Nothing for the search to switch on.** We have no MetaMorpheus PRs. #1338 is a library API that MetaMorpheus does
  not call.

Ancestry checked on upstream with `git merge-base --is-ancestor <sha> <tag>`: 1.0.594 = `b1e925ff`, 1.1.12 = `2591d745`
(pins mzLib 1.0.594).

## In 1.0.594 / 1.1.12

### 1. mzLib #1337: protein N-terminal occupancy counts Met-removed forms (PXR-LG1)

- **PR / sha / release:** smith-chem-wisc/mzLib#1337, merge `b4361297`, first released in mzLib 1.0.592; carried by
  1.0.594 and therefore by MetaMorpheus 1.1.12. Not in 1.0.591 (your 1.1.11 pin).
- **What it does:** a form starting at residue 2 after an initiator `M` (e.g. `Ac-ASTE...` from `MASTE...`) now counts
  toward protein position 1 (the N-terminus) in both the numerator and denominator of `CalculateParentLevelOccupancy`;
  before, such forms were dropped, so N-terminal occupancy reflected Met-retained forms only, or was absent.
- **How to switch it on:** nothing to set. MetaMorpheus 1.1.12 reaches it through `ProteinGroup.PopulateSampleGroupResults()`
  in `PostSearchAnalysisTask` (and the glyco post-analysis); it shows up in the protein-group occupancy columns.
- **Recommendation: adopt now** (it comes with the bump and cannot be turned off). PXR-LG1 asks only that you record
  it as a known result change in your 1.1.11 -> 1.1.12 switch notes, so nobody reads the N-terminal shift as a regression.
- **Traps:**
  - Values go **up or appear** at `pos0` for proteins whose N-terminus was seen Met-removed (the common Ac-N-term case).
    Mixed-version results are not comparable at that site; other sites are unchanged.
  - A protease cleaving C-terminal to Met (CNBr, `M|`) yields residue-2 forms from Met-retained molecules; they are
    counted as the N-terminus, so N-terminal occupancy may be understated for such digests. Documented, not guarded.
    Irrelevant for tryptic searches.
  - The rule is Protease's own: residue 1 must be `M`. A residue-2 start for any other reason (trypsin after `K1`) is
    unchanged.

### 2. mzLib #1338: resolve proteins to stable Ensembl gene ids against a pinned gene set (PXR-LG2)

- **PR / sha / release:** smith-chem-wisc/mzLib#1338, merge `5d772a23`, first released in mzLib 1.0.592; in 1.0.594.
- **What it does:** maps each protein to stable Ensembl gene ids (one row per accession x gene, one of six outcomes,
  never picking one gene) against a gene set pinned to one Ensembl release, with full sha256 provenance.
- **How to switch it on:** mzLib API only: `Protein.EnsemblGeneIds`, `EnsemblGeneSet.LoadGtf` /
  `EnsemblGeneSetReader`, `EnsemblXrefTable.Load`, `EnsemblGeneResolver` + `GeneResolutionTsv`. pyMzLib exposes
  `resolve_genes`. No MetaMorpheus flag or TOML key.
- **Recommendation: not for the pipeline search.** MetaMorpheus does not call it, and it does not change any search
  output. It belongs at ingest/analysis time on the search database, which aging/dataRepo own. If you ever run it, it
  is a post-search step, not part of the MM bump.
- **Traps:** pass the Ensembl xref table, or `ensembl_xref_agrees` is null everywhere and aging's default view is empty.
  `LoadProteinXML` applies variants by default, so counts are of proteoforms (human: 52,359 from 20,416 entries); say
  which. Contaminants are never mapped. Rat resolves poorly by any source (59.6% of reviewed entries by Ensembl's xref).

## Separate from mzLib/MM: the orthology snapshot at ingest

Not part of the search, but it touches your ingest/publish: our released orthology snapshot (`compara-116`, tar
`b1d682a5...`, manifest `fd0a9d8f...`) is registered **once per datarepo store** with
`datarepo run logs.register_orthology --store <store> --input snapshot_tar=compara-116.tar --input snapshot_manifest=compara-116.manifest.json`
(datarepo 1.3.0, dataRepo 032). It takes no accession and copies no rows. dataRepo's 093 to aging asks aging to
register it during the 1.3.0 switch. If your publish creates or rebuilds a store, that store needs this one run; no
search re-run is involved. No ask: FYI.
