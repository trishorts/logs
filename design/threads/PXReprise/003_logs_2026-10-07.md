## 1. Gene resolution at ingest: inputs and release pins we own (PXR-O3)

- **What / where:** under dataRepo's D24 route (agreed in our 015-logs), dataRepo runs our released resolver (mzLib
  #1338, via pyMzLib) once per (`search_database_sha256`, `gene_set_release`). It does not run per search. We own
  the logic, the gene-set tables, the xref input and the release choice. The pinned gene sets are Ensembl **116**:
  `results/gene_sets/{Homo_sapiens.GRCh38,Mus_musculus.GRCm39,Rattus_norvegicus.GRCr8}.116.genes.tsv.gz` in
  trishorts/logs. Human reference output: `results/search_db_human_e116.tsv.gz`.
- **How it touches you:** the key is the search database's sha256. Changing the search database (a new UniProt
  release, an added species, contaminant or variant settings) means a new resolution at ingest. The search itself is
  unaffected. A species without a gene set from us (anything but human/mouse/rat) cannot be resolved until we build one.
- **Recommendation: no change now.** Tell us in this thread **before** you change the search database or add a
  species, so the gene set and xref are ready.
- **Traps:**
  - pyMzLib `resolve_genes` resolves entries, not proteoforms (human 20,899 rows vs 53,239 from the C# tool).
  - Without `xref=`, `ensembl_xref_agrees` is null everywhere and aging's default view is empty; the v1 definition
    requires the xref input.
  - A row's `gene_set_sha256` is the GTF's sha256, not the table's.

## 3. mzLib #1382 (open): variant proteoform accession -> parent entry (PXR-O5)

- **PR / sha / release:** smith-chem-wisc/mzLib#1382, **open**, not in any release.
- **What it does:** adds `VariantApplication.ParseAccession`, which turns `P12345_S70N_A80T` into the parent entry
  `P12345` plus the applied variants, keeping both. RefSeq accessions (`NP_000537.3_R72P`) are handled.
- **How it touches you:** after it merges, ships in an mzLib release and is projected into pyMzLib, dataRepo's ingest
  can join variant-proteoform identifications to their entry's genes and orthologs. Today those identifications have no
  entry-level join. This only matters if your search database is loaded with variants applied.
- **Recommendation: adopt later.** It waits on the merge, then an mzLib release, then the pyMzLib projection, then
  dataRepo picking it up. We will post here at each of those steps. PXR-O5 asks whether the pipeline search loads
  variants, so we know if this affects you.
- **Trap:** `P12345_2` is a ProteinDbLoader duplicate-accession counter, not a variant, so it is deliberately left
  unrecognized. Never cut at the first `_`.
