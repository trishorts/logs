## 1 - The row, in short

| column | meaning |
|---|---|
| `search_database_sha256`, `accession`, `position`, `residue` | your site, plus the residue we read from the database |
| `edge_kind` | `homolog` (between genes, from the store), `isoform` (isoform entry to its canonical entry), or `variant` (a guard: your 004 found 0 variant sites) |
| `target_search_database_sha256`, `target_accession`, `target_position`, `target_residue` | the target; position and residue are null exactly when the row is a refusal |
| `outcome` | exactly one value (section 2) |
| `gene_id`, `target_gene_id` | from gene resolution, under the agrees view |
| `homology_id`, `relationship_type`, `orthology_snapshot_id` | the store row, verbatim (`homolog` only), so your network edge can carry `ortholog_one2one` vs `ortholog_one2many` vs a paralog type |
| `ensembl_protein`, `ensembl_position`, `target_ensembl_protein`, `target_ensembl_position` | the intermediate coordinates (`homolog` only) |
| `msa_sha256`, `aligner`, `gene_set_sha256`, `target_gene_set_sha256` | provenance |

**Why there are Ensembl columns.** A `homolog` row is three coordinate changes along one relationship:
your UniProt entry to its gene's Ensembl protein (our pairwise alignment), then the column of
Compara's gene-tree alignment to the other gene's Ensembl protein, then to each UniProt entry of that
gene in the target database (our pairwise alignment again). Only the middle step crosses a homology
edge. Carrying the intermediate positions lets you see which step failed.

## 2 - Outcomes

| outcome | meaning |
|---|---|
| `identical` | aligned, same amino acid |
| `substituted` | aligned, different amino acid (see LOGS-P6) |
| `residue_mismatch` | the residue you gave is not at that position in the source entry. Nothing is mapped |
| `position_out_of_range` | beyond the source sequence |
| `gene_not_resolved` | the source accession has no gene; the resolution's outcome is carried |
| `no_homolog` | no store row of the requested kind; the store's `pair_status` is carried |
| `not_on_ensembl_protein` | step 1 failed: the residue is where UniProt and the Ensembl protein differ |
| `gap_in_target` | step 2: the alignment column is a gap in the target protein |
| `not_on_target_entry` | step 3: the target Ensembl residue has no counterpart in that UniProt entry |
| `target_gene_not_in_database` | the target gene has no entry in the target database |
| `isoform_specific` | your fibronectin EDA/EDB/IIICS and lamin C cases |
| `variant_changed_span` | inside an indel's changed span (a guard) |

`residue_mismatch` exists because your site key already carries the residue. It is a cheap check that
catches isoform-versus-canonical coordinate confusion before it reaches a network.

## 3 - Questions

**LOGS-P5 - which target databases first?** A row names a target database, because a target position
is on an entry as that database holds it. We propose to start with aging's three reviewed
proteomes, whose gene resolutions are already pinned (human `760984e8...`, mouse `fb52debf...`, rat

**LOGS-P6 - do you want `substituted` rows?** We propose yes: an aligned column with a different
residue (S to T, S to A) is reported with both residues, and deciding whether that conserves the
site is yours. The alternative is to refuse it, which would hide the information you need for that
call. Tell us if you would rather filter it on our side.
