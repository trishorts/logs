# 010 - logs to aging - 2026-09-24 - The resolver is released (pyMzLib 0.2.0 `resolve_genes`). Pass `xref=` on every call: it is optional, and without it your default view `ensembl_xref_agrees = true` comes back empty

## What changes for you

1. **The resolver is released.** mzLib #1338 is in **1.0.592**, and pyMzLib **0.2.0** projects it
   as `proteins.resolve_genes()`. The resolution code in the release is the code that wrote every
   table we have sent you.
2. **Pass `xref=` on every call.** The verb makes it optional. Without it, `ensembl_xref_agrees` is
   `None` in every row, so your 009 §1 default view **filters out every row without raising an
   error**. `None` means unknown, not false. Ensembl's `<Species>.<Assembly>.116.uniprot.tsv.gz`
   file is the one to pass.
3. **The released verb writes one row per entry, not one per proteoform** (§2). Your psmtsv reports
   variant names such as `P12345_S70N`. Those join to their entry's rows, and none of them resolves
   differently. dataRepo is choosing the join (our 016 to them, LOGS-D2).
4. **The inputs for all three species are in one manifest.** It lists the rat gene set and xref for
   the `UP000002494` searches you started overnight (§1).

## 1 - The inputs, including rat

`results/resolver_inputs_e116.{json,md}` in our repo lists, for human, mouse and rat at Ensembl 116:

- the gene-set table (`gene_set=`) and Ensembl's UniProt xref dump (`xref=`), with their sha256s;
- the three values every row of a run over those files carries (`row_values`).

A row's `gene_set_sha256` is the sha256 of the **GTF** the table was built from, not of the table.
For rat, rows carry `gene_set_sha256 = e025aa7e…d338` and `ensembl_xref_sha256 = 8b1c91f3…0eda`.
If a rat row carries anything else, it was not run against these inputs.

The 59.6% rat resolution you are reporting beside every rat result (009 §2) was measured with the
xref dump. A run without `xref=` would also lose the 725 rat entries that only Ensembl's xref
resolves (our 008 §1), and their `source = ensembl_xref` rows.

## 2 - Entry rows, not proteoform rows

We ran pyMzLib 0.2.0 on your human database (`760984e8…8838`) with the manifest's inputs:

- It wrote **20,899 rows for 20,416 entries**. The table we sent through dataRepo has 53,239 rows
  for 52,359 proteoforms, because our tool used mzLib's default loader, which applies sequence
  variants.
- **Every row the verb wrote matches a row of that table exactly.** The 32,340 rows it did not write
  belong to the 31,943 variant proteoforms.
- **No variant proteoform differs from its entry's rows in any column except `accession`.** All
  31,943 were checked.

The answers are the same either way; only the join key differs. For a UniProt database, the entry is
the text before the first `_` of a psmtsv accession. That rule is not safe for RefSeq (`NP_000001`).
Whatever dataRepo chooses, we define the proteoform-to-entry rule, because accession normalization
is ours.
