## REQ-AGING-5 · **Zero isoform suffixes, and not by luck — the database cannot produce one**

dataRepo's measurement over the nine datasets is right, and we can give you the mechanism rather than
a second count of the same thing. Read from the pinned `.xml` itself:

```
<accession> elements          91,042
  ... containing a "-"             0
<isoform> elements            33,097
```

**Zero of 91,042.** The reviewed proteome XML describes isoforms (33,097 of them) as `<isoform>`
elements inside a canonical entry; it does not carry them as separate accessions with sequences. So
no search against this database can emit `P12345-2`, and none did. It is a property of the database,
not of our corpus, which is why it holds for every dataset we have and every one we will add on this
database.

**What will change it, and we will tell you when it does.** Our D8 has `db_prepare` appending
*targeted* isoform sequences to the database — the isoform-specific peptides are half of how we infer
proteoforms at all (D14). It is not implemented. When it lands, the database hash changes, so your
key already distinguishes before and after, and suffixed accessions appear only from that hash
onward. **Normalization stays in scope, as a column beside the verbatim accession — agreed, and your
framing of "same protein *for this question*" as ours to decide per question is exactly right.**

## REQ-AGING-6 · **A versioned table, joined on `(accession, search_database_sha256)`. Both ENSG forms.**

A table, not a call. Three reasons, all the same reason:

- A join against a pinned table is reproducible; a call is a service whose answer can change under a
  paper. Your own key already says this.
- Our numbers each carry a definition id and a version, and a table can carry one. A call cannot,
  except by convention.
- It is the same rule we applied to your `--one-to-one-only` question and you applied to ours: what a
  file *contains* must not depend on when it was asked.

**Carry both the versioned `ENSG00000063438.21` and the stable `ENSG00000063438`.** Your lean is
right. We will join on the stable id — versions move for reasons that are not biology — but the
versioned one is the only thing that makes the row auditable against a specific Ensembl release, and
dropping it would be the same mistake as printing a q-value to six decimals and losing the seventh
(our S36). Two columns, both present, and let each consumer pick.

## REQ-AGING-8 · **Carry the UniProt gene name for the 1,012. Outcome stays `not_in_source`.**

Yes to your proposal, and we think it is the answer your own §REQ-AGING-3 reasoning forces.

Our 002 said we would stop reading the producer's symbol entirely. That was about **provenance, not
about symbols**: the `Gene Name` column is untrustworthy because MetaMorpheus writes it per dataset
and it comes out ragged — 182 ragged rows, 60 accessions named in one dataset and null in another with
nothing about the data differing. **Your proposal removes exactly that defect**: the same name, read
once from bytes pinned by a sha256, cannot be ragged across datasets, because there is only one read.

And dropping it would create precisely the failure we asked you to protect us from. A protein with
evidence at protein level and no gene at all is indistinguishable, to a reader, from a protein nobody
looked up — and *"no gene id exists"* versus *"no lookup was attempted"* is the distinction your four
outcomes exist to preserve. A row that says `not_in_source` **and** carries `ERVK-21` says both true
things. A row that says `not_in_source` and nothing else throws one of them away.

Two conditions, both of which you have already proposed:

- **The outcome column stays `not_in_source`.** The symbol is a label, never a key, and never a
  substitute for the missing id.
- **It comes from the pinned database**, not from our search output. If those two ever disagree we
  want to hear about it, because that is a MetaMorpheus defect and ours to carry upstream.
